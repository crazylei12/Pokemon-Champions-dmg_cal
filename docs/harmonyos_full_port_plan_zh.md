# Pokémon Champions Assistant 鸿蒙完整移植与验收方案

日期：2026-07-31

状态：阶段 0 已完成；阶段 1 模拟器范围已完成、真机门延期；阶段 2–8 已完成可实现与模拟器验收范围；阶段 6–8 相册真实取帧、识别、捕获隔离与浮窗触摸真机门延期；阶段 9 待实施

目标分支：`feature/harmonyos-port`

## 1. 目标与边界

本次工作把现有 Pokémon Champions Assistant 的 Android 标准版和录屏功能版完整移植到 HarmonyOS。移植后的产品行为、数据语义、识别结果、伤害计算结果和用户可见功能应与原应用一致，不新增产品功能，不顺手修改文案、算法或交互，也不改动 Android 两个现有分支。

当前源码基线：

- 标准版：`main`，冻结基线提交 `1e930cabcfb70605e9de7acd68f97674d8b694f5`；
- 录屏功能版：`feature/battle-replay-phase-4`，冻结基线提交 `dd1fa47a6034f80b5cba3488a547f8d7dc56b252`；
- 鸿蒙移植：独立工作树 `pokemon-champions-assistant-harmonyos` 和分支 `feature/harmonyos-port`；
- Smogon 伤害引擎继续固定在当前子模块提交，不升级算法或数据源。

范围内功能包括：

1. 首页、自由计算、对局助手、设置四个主入口；
2. 我方队伍两页 OCR 录入、逐项人工修正、完整性校验、命名保存和切换；
3. 双方各 6 只队伍预览识别、Top-3 候选、搜索修正和人工确认；
4. 普通悬浮球、悬浮菜单和完整实战伤害面板；
5. 可选战斗 HUD、单打/双打、速度排序、戏法空间、拖动、缩放、横竖屏独立布局、隐藏和再战；
6. 双向伤害、HP 区间、击倒次数、速度线、天气、场地、状态、能力等级、墙、范围招式和要害等现有计算项；
7. 已保存我方队伍和对手宝可梦配置的创建、搜索、编辑、删除、排序、形态共享与引用清理；
8. 整包备份、恢复、对手配置单独分享、旧备份兼容和系统备份能力；
9. 用户主动检查更新及标准版/录屏版选择；
10. 录屏功能版的“识别并录屏”“仅识别”“仅录屏”、应用内部音频、MP4 保存、回放入口和异常收尾。

明确不做：

- 不新增游戏操作、自动点击、代打、联网同步、云端识别或账号系统；
- 不修改 Pokémon Champions，不注入、不 Hook、不读取游戏内存、不拦截网络；
- 不趁移植调整现有识别阈值、伤害规则、配置共享规则或产品文案；
- 不把测试用“相册、测试图片、ROI、OCR、Top-3 文件名”等调试概念暴露到正式产品界面；
- 不把个人截图、识别缓存、保存队伍或验收产物提交进 Git。

## 2. 完成定义

只有同时满足以下条件，才视为“鸿蒙端完整移植完成”：

- 标准版和录屏功能版均能在干净环境构建出可安装的 HarmonyOS 包；
- 原应用所有用户可见入口均有鸿蒙对应实现，没有空按钮、占位页或静默降级；
- 相同输入经过 Android 与 HarmonyOS 后，核心 JSON、候选排序、伤害结果和存储状态满足既定等价规则；
- 鸿蒙端可导入 Android 导出的现有备份与对手配置分享文件，且不会丢失或错误合并数据；
- 用户指定的相册全屏图片验收全部通过，不依赖在开发模拟器安装游戏；
- 录屏功能版能以相册中播放的本地测试视频完成屏幕和内部音频录制、保存、打开和异常收尾验收；
- 自动化测试、静态检查、干净构建、安装启动、旋转和进程重启回归全部通过；
- 仍需真机才能证明的系统能力若存在，必须明确列为未关闭验收门，而不能以模拟器构建成功代替。

## 3. 总体技术映射

下表是移植方向，不代表在能力探针完成前锁死具体 API：

| Android 现有实现 | HarmonyOS 目标实现 | 等价要求 |
| --- | --- | --- |
| Compose / Activity | ArkUI / UIAbility | 页面、状态和交互语义一致 |
| Foreground Service | UIAbility 配合后台任务或系统允许的长时任务 | 截图会话生命周期可见、可停止、不可静默恢复 |
| MediaProjection / ImageReader | AVScreenCapture 原始帧能力 | 用户授权、单窗口捕获、原始尺寸、旋转和资源释放一致 |
| `TYPE_APPLICATION_OVERLAY` | `TYPE_FLOAT` 悬浮窗口 | 悬浮球、面板、HUD、触摸和布局行为一致 |
| ML Kit 中英文 OCR | Core Vision 文本识别 | 中文、英文、数字、行块坐标和离线复测满足字段识别要求 |
| OpenCV Java | OpenCV Native/C++ | 使用同一模板和 ROI，候选及置信度计算保持一致 |
| WebView + 本地 JS | ArkWeb + 本地 JS | 固定 Smogon 引擎输入输出一致，不改计算规则 |
| SharedPreferences / 私有 JSON | Preferences / 应用沙箱文件 | 数据结构、原子写入、损坏保护和清理规则一致 |
| Storage Access Framework | DocumentViewPicker 等系统文件选择器 | 导入、导出、取消、大小限制和错误反馈一致 |
| Android Backup | BackupExtensionAbility | 只备份允许的数据，不备份截图、缓存或临时会话 |
| MediaCodec / EGL / AudioRecord / MediaStore | AVCodec、图形路由、应用播放音频和媒体库接口 | 录像参数、隔离、同步、收尾和相册可见性一致 |

原则上优先复用不含 Android 依赖的原始资源和协议：稳定 ID、JSON schema、中文本地化数据、伤害引擎 JS、Champions 预设、ROI 配置、模板二进制和测试向量。平台相关 UI、权限、窗口、取帧、媒体和存储层再做鸿蒙原生实现。

## 4. 分阶段实施与验收

每一阶段都有独立退出条件。原则上前一阶段的阻断门未关闭，不进入依赖它的后续功能堆叠。若用户因客观缺少真机而明确要求继续，可先推进不依赖真机结论的工程和业务层，但必须保留未关闭门、禁止删除对应功能，并在最终完成定义中继续报告为未验收。

要做到：

- 给标准版和录屏功能版建立逐入口、逐状态、逐文件格式的功能清单；
- 为数据模型、伤害请求/响应、我方 OCR 中间结果、队伍预览候选、保存配置、对局状态和备份文件各保存一组去隐私化黄金输入输出；
- 记录 Android 当前行为中必须保持的细节，例如我方确认配置优先于静态合法性快照、用户保存的对手配置位于顶部且按保存顺序排列、重新识别新局时清空旧局状态；
- 明确标准版和录屏版唯一差异，避免鸿蒙端形成两套漂移代码。

交付物：

- 功能对照矩阵；
- 跨平台 JSON 契约及黄金测试向量；
- 两个产品变体的差异清单；
- 第三方依赖和许可证清单。

验收：

- README 中所有用户可见功能均能映射到至少一条实现任务和一条验收项；
- Android 两个基线提交可重现现有自动化测试结果；
- 黄金样本不含个人数据、原始游戏截图或不可提交素材；
- 没有任何“移植时顺便优化”的范围混入。

### 阶段 1：系统能力探针和技术闸门

要做到：

- 验证普通开发签名或目标发布签名能否获得 `ohos.permission.SYSTEM_FLOAT_WINDOW` 并创建 `TYPE_FLOAT`；
- 验证应用内 AVScreenCapture 能通过系统选择器只捕获相册窗口，并获得方向正确、尺寸为 `2772×1240` 的原始帧；
- 验证悬浮球、悬浮菜单、伤害面板和 HUD 不会进入被捕获画面；
- 验证 Core Vision OCR 能读取相册图片的中文、英文、数字和文本坐标，并在断网后的第二次运行仍满足本地识别要求；
- 验证 OpenCV Native 能分别为模拟器和目标真机构建，并正确读取现有模板二进制；
- 验证 ArkWeb 能加载打包内的固定伤害引擎并稳定执行本地 JavaScript；
- 验证系统文件选择器、应用沙箱、备份扩展、媒体库写入和更新下载所需能力；
- 验证录屏原始帧、H.264、内部应用音频、AAC、MP4 以及正常/异常停止链路。

交付物：

- 一个只用于开发验证的能力探针包；
- 每项能力的日志、截图或输出文件；
- 权限、签名、模拟器与真机差异结论；
- 所有阻断项的处理决定。

验收：

- 浮窗能创建、交互和彻底移除，拒绝权限时有可恢复路径；
- 相册单窗口捕获连续 20 次没有黑帧、横倒、裁切或尺寸漂移；
- 捕获帧不含助手自己的浮层；
- OCR、OpenCV 和 ArkWeb 各用固定输入得到稳定结果；
- 录制 3 分钟测试视频后生成可播放 MP4，音视频同步且助手浮层不入画；
- 强制停止、撤销授权、旋转和编码失败后无残留浮窗、未完成媒体文件或不可恢复会话；
- 若模拟器不支持某项应用级媒体能力，必须在真实 HarmonyOS 设备上关闭该门；不能删除对应原功能或把失败当作已完成。

## 5. 最终相册全屏验收方案

### 5.1 固定环境

- HarmonyOS 模拟器系统：当前已配置的 OpenHarmony 6.1.1 / API 24；
- 模拟器实例：`PokemonChampions_Photo_1240x2772`；
- 竖屏物理分辨率：`1240×2772`；
- 验收时旋转到横屏，渲染分辨率应为 `2772×1240`；
- 图片源：现有 20 张 `2772×1240` 样本，其中 12 张组成六组我方两页 OCR，8 张为双方队伍预览；
- 视频源：一段包含可核对画面、立体声测试段和静音测试段的本地 MP4；
- 只安装系统相册、鸿蒙候选包和必要系统组件，不安装游戏。

### 5.2 图片准备

1. 用 `hdc` 或 DevEco Studio 官方导入方式把验收图片和视频上传到媒体库；
2. 打开系统相册，确认文件顺序和像素尺寸；
3. 将模拟器旋转到横屏；
4. 打开单张图片，点击画面中央隐藏相册工具栏；
5. 确认没有状态栏、导航栏、工具栏或缩放手势造成的画面压缩；
6. 启动助手截图会话时，在系统选择器中只选择相册窗口。

### 5.3 1:1 分辨率门槛

第一轮必须使用图片与横屏渲染分辨率完全一致的 `2772×1240` 配置：

- 捕获结果必须报告 `width=2772`、`height=1240`；
- 图片不能被拉伸、裁切、二次缩放或加非预期黑边；
- 相册控件必须隐藏，助手浮层不得进入捕获帧；
- 若无法真正全屏，先调整模拟器实例分辨率或系统栏策略，再重新开始；不得缩放验收图片来迁就错误的模拟器画布。

1:1 全部通过后，再增加一个非 1:1 屏幕配置，验证“最大居中 16:9 游戏画布”映射没有只对固定分辨率硬编码。第二轮允许预期的居中留边，但不得拉伸游戏画面。

### 5.4 执行顺序

1. 冷启动标准版，启动普通截图会话并授权相册单窗口；
2. 逐组打开六组我方队伍图片，完成两页 OCR、人工确认、命名保存和切换；
3. 逐张打开 8 张队伍预览图片，完成双方 12 槽识别、Top-3 检查、搜索修正和确认；
4. 在确认后的静态相册画面上打开完整伤害面板，逐项检查双方计算和状态调整；
5. 结束会话，重新启动为 HUD 模式，复测单打/双打、速度、伤害、布局和再战；
6. 导出整包备份和对手配置分享文件，清空应用数据后重新导入并逐项比较；
7. 安装录屏功能版覆盖标准版，确认数据保留和共享功能不变；
8. 在相册播放本地测试视频，依次验证三种会话模式和 MP4 输出；
9. 撤销权限、旋转、强制停止并重启，验证恢复和清理；
10. 切换到非 1:1 模拟器配置，重复双方队伍预览识别和 HUD 布局核心用例。

### 5.5 证据格式

每个用例至少记录：

- 候选包版本、Git 提交、变体、模拟器实例和系统版本；
- 输入图片/视频的文件哈希与像素尺寸；
- 捕获帧尺寸、方向、所选窗口和是否存在浮层污染；
- 自动识别结果、人工真值、需要修正的字段和最终确认结果；
- 伤害请求/结果 JSON、关键界面截图和耗时；
- 录像文件的编码、分辨率、帧率、时长、音轨、大小和播放结果；
- 通过、失败或阻断，以及失败后的复测版本。

验收截图、视频、日志和用户数据放在 Git 忽略目录或仓库外 D 盘验收目录，不提交到公共源码。

## 8. 已知高风险门

1. **浮窗授权**：当前 SDK 把 `SYSTEM_FLOAT_WINDOW` 标记为 `system_basic`。必须先证明目标签名和设备允许正式应用使用，不能等 UI 完成后才发现无法发布。
2. **单窗口原始帧**：识别要求原始尺寸、正确旋转和浮层隔离。模拟器支持系统相册不代表应用级 AVScreenCapture 原始帧一定可用。
3. **模拟器录屏能力**：DevEco 模拟器自身不提供的录屏功能不必然等于应用 API 不可用，但必须实测；若不可用，录屏门要转到真实 HarmonyOS 设备关闭。
4. **OCR 等价性**：Core Vision 与 ML Kit 的分词、字符和坐标不同，必须通过字段级规则和黄金样本适配，不能只比较一段整页文字。
5. **OpenCV 数值漂移**：Java 与 C++、不同 ABI 的浮点和颜色转换可能影响小分差候选，必须对候选全列表和分数做差异分析。
6. **ArkWeb 生命周期**：本地 JS 引擎需处理页面未就绪、进程回收和并发请求，避免错误结果写入当前对局。
7. **内部音频策略**：播放应用和系统策略可能禁止内部音频捕获。必须以实际非静音 PCM/AAC 为准，不用麦克风伪装成功。
8. **跨平台备份**：文件选择器 URI、编码和原子写入语义不同，恢复前必须完整验证，不能边解析边覆盖本地数据。

风险门失败时先保留证据并解决平台权限、签名或 API 路径；不能删除功能、静默降级或把测试入口包装成正式功能。
