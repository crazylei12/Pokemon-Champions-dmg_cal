## 1. 目标和完成定义

本次工作不是继续证明“移植代码已经存在”，而是以当前 Android 产品行为为真值，对 HarmonyOS 端做一次独立、可追溯、可复测的全量审计，回答以下问题：

1. Android 标准版已有的每个用户功能，在 HarmonyOS 标准版是否真的可达、可用且结果等价；
2. Android 录屏版相对标准版的专属能力，在 HarmonyOS 录屏版是否保持相同产品边界；
3. HarmonyOS 是否存在漏移植、错误移植、静默降级、权限过度、数据不兼容、生命周期错误、界面不合理或发布风险；
4. 现有阶段文档、66 项功能矩阵、59 项自动化与模拟器证据，能否独立复现并真正支撑各自结论；
5. 哪些项目能够在代码、测试或模拟器中关闭，哪些项目必须在 HarmonyOS 真机上完成；
6. 每个异常的严重性、影响范围、复现步骤、Android 对照证据、HarmonyOS 证据、修复建议和回归要求是什么。

只有同时满足以下条件，最终报告才可写“全量审计完成”：

- 本文所有检查项都有 `PASS`、`FAIL`、`BLOCKED` 或 `NOT_APPLICABLE` 之一，不能留空；
- 每个 `PASS` 都达到该能力所需的最低证据等级，不能用源码存在或测试页展示代替真实产品路径；
- 每个 `FAIL` 都有可复现证据和影响分析；
- 每个 `BLOCKED` 都写明缺少的设备、账号、签名、系统能力或测试素材，以及解除阻塞后的唯一复测步骤；
- HarmonyOS 标准版和录屏版分别检查，不能用其中一个变体代替另一个；
- 代码、数据、界面、权限、构建、升级、异常恢复和真机交互均覆盖；
- 最终结论基于审计时的最新提交和重新生成的证据，不沿用过期哈希或旧截图。

## 4. 证据、状态和缺陷分级

### 4.1 证据等级

| 等级 | 含义 | 可以证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| E0 | 文档、自报矩阵、设计说明 | 预期和作者声明 | 代码存在或功能正常 |
| E1 | 当前提交源码逐行审阅、静态检查、产物内容检查 | 实现路径、权限声明、资源和明显逻辑风险 | 运行时行为和系统交互 |
| E2 | 执行业务代码的单元/契约/黄金向量测试 | 确定性逻辑、序列化、算法等价 | 正式页面、系统权限、设备能力 |
| E3 | 正式产品路径的模拟器运行与可复现日志 | 页面、沙箱、ArkWeb、Native x86_64、部分生命周期 | 真机硬件、浮窗触摸、真实捕获、内部音频 |
| E4 | 模拟器/真机截图、录屏和人工交互对照 | 布局、可达性、触摸、键盘、旋转体验 | 未覆盖的异常和长期稳定性 |
| E5 | 发布配置的 ARM64 真机端到端黑盒验收 | 用户最终路径、真实权限、OCR、录制、升级和系统集成 | 未测试设备/系统版本的普遍性 |

系统截屏、OCR、浮窗、录屏、媒体库和发布升级项目的最终 `PASS` 至少需要 E5。纯数据和纯算法项目可在 E2 达成，但必须使用与 Android 同一输入向量并核对完整输出。

### 4.2 状态

- `PASS`：达到该项最低证据等级，结果满足明确验收标准；
- `FAIL`：已证实实现缺失、错误、不合理或与 Android/产品约定不一致；
- `BLOCKED`：当前缺少不可替代的设备、签名、素材或系统能力；
- `NOT_APPLICABLE`：经产品边界确认不应在该变体出现；
- `NOT_TESTED`：仅允许执行中的临时状态，最终报告不得保留。

不要使用模糊的“基本通过”或“部分通过”。若一个检查项只有一部分成立，拆成两个独立项。

### 4.3 缺陷等级

- `P0`：隐私/权限越界、数据不可恢复损坏、发布签名或升级链断裂、错误结果可能大规模误导用户；
- `P1`：核心流程不可用、OCR/图像/伤害结果错误、标准与录屏变体串线、稳定崩溃；
- `P2`：旋转/生命周期/浮窗/键盘/性能问题，或重要但可绕过的功能异常；
- `P3`：视觉、文案、无障碍、轻微一致性、测试和维护性问题。

## 6. 执行顺序与阶段门

### 阶段 A：冻结 Android 真值

1. 在 Android 标准版和录屏版分别运行当前单元测试、TypeScript/数据测试和 `git diff --check`；
2. 读取所有用户可见入口、Manifest、备份规则、持久化 schema、更新选择和录屏契约；
3. 对 66 项功能逐项补齐 Android 源码、测试和可运行路径；
4. 记录标准版与录屏版唯一差异，不把录屏专属实现误当共享基线；
5. 生成或确认跨平台黄金 JSON、OCR 人工真值、队伍预览候选真值、伤害结果和存储样本；
6. Android 基线未明确的项目先标为待产品判定，不自行把 HarmonyOS 行为当成标准。

退出条件：每个后续 HarmonyOS 检查项都能指向具体 Android 期望或明确的平台特例。

### 阶段 B：HarmonyOS 静态映射和构建审计

1. 把每个 Android 入口映射到 ArkTS/ArkUI、Native/C++、ArkWeb、存储、权限或系统 API；
2. 审阅标准/录屏产品开关是否真正裁剪功能和权限；
3. 运行严格编译、Native 双 ABI、许可证、资源哈希、包内容、未签名/签名和版本一致性检查；
4. 检查未使用占位、Debug 验证页、静态假结果、硬编码路径和测试后门；
5. 重新评估所有旧阶段 `PASS`，不继承 `bbdf55c` 的结论。

退出条件：没有未映射的 Android 用户入口；所有 HarmonyOS 文件都有明确产品用途或清理建议。

### 阶段 C：纯逻辑和跨平台数据等价

1. 对同一黄金输入同时执行 Android 与 HarmonyOS 逻辑；
2. 比较规范 ID、候选排序、阈值、伤害请求/响应、存储 JSON、迁移和错误结构；
3. 对每个不一致定位为平台合理差异、遗漏、算法漂移或测试不足；
4. 禁止只比较少数字段或只验证 JSON 能解析。

退出条件：所有纯逻辑项目达到 E2，或记录为 `FAIL`。

### 阶段 D：正式 UI、模拟器和视觉对照

1. 从干净安装进入正式页面，不通过隐藏验证页代替用户路径；
2. 在固定数据集下逐页生成 Android 与 HarmonyOS 截图；
3. 对齐信息层级、按钮语义、状态、滚动、弹窗、键盘、错误/空态和无障碍；
4. 在竖屏、横屏、不同分辨率、字体缩放和进程恢复下复测；
5. 每个可点击控件都执行一次成功、取消、重复点击和返回路径。

退出条件：所有非真机专属 UI 达到 E3/E4，且没有 Release 可见调试内容。

### 阶段 E：HarmonyOS 真机黑盒

1. 使用 ARM64 真机、发布候选签名和两产品变体；
2. 完成截屏、Core Vision OCR、Native 图像识别、浮窗、旋转、录屏、内部音频、媒体库和升级；
3. 覆盖权限拒绝/撤销、锁屏、后台、强杀、目标应用关闭、低空间和断网；
4. 完成固定相册样本、非 1:1 屏幕、30 分钟稳定性和标准/录屏覆盖安装；
5. 保留由用户亲自确认的系统隐私提示证据，自动化不得代点授权。

退出条件：所有要求 E5 的项目为 `PASS` 或带明确解除条件的 `BLOCKED`。

### 阶段 F：报告、修复优先级和复测

1. 先报告 P0/P1，再报告 P2/P3；
2. 区分确定缺陷、设计不合理、测试缺口、发布阻塞和设备限制；
3. 修复后只关闭有新证据的条目，并对相邻功能做回归；
4. 所有修复完成后重跑全矩阵、双变体构建、包检查和工作树检查；
5. 最终报告明确“可发布”“不可发布”或“仅模拟器范围通过”，不得混用。

## 8. 设备、方向与状态组合矩阵

### 8.1 最低设备集合

| 平台 | 设备 | 变体 | 主要用途 |
| --- | --- | --- | --- |
| Android | 当前可复现的手机 | standard | 冻结标准产品行为与截图 |
| Android | 当前可复现的手机/平板 | replay | 冻结捕获、录屏、HUD 和大屏行为 |
| HarmonyOS | API 24 x86_64 模拟器 | standard + replay | 构建、页面、ArkWeb、存储、Native 基础和可自动化 UI |
| HarmonyOS | ARM64 真机 | standard + replay | 权限、截图、OCR、浮窗、旋转、音频、录屏、媒体库和升级 |

若只有一台 HarmonyOS 真机，最终报告必须注明设备局限，不能外推为所有设备通过。

### 8.2 每个核心流程都要覆盖的状态

- 首次安装、已有数据升级、standard/replay 覆盖安装、卸载重装；
- 竖屏启动后横屏、横屏启动后竖屏、连续旋转、后台旋转；
- 默认字体、放大字体、显示缩放、系统栏/刘海/圆角安全区；
- 权限未申请、允许、拒绝、设置撤销、会话中撤销；
- 有网、断网、超时、GitHub 错误；
- 空数据、正常数据、大量数据、损坏数据、旧 schema；
- 冷启动、热启动、前后台、锁屏、进程强杀、系统回收；
- 单打、双打、普通浮窗、HUD、隐藏恢复、再战；
- standard 与 replay 各自重复，不共享前一次内存状态。

## 9. 首轮高风险审计入口

以下只是优先检查入口，不是预先判定为缺陷：

1. 阶段 10 验收矩阵的源码提交早于当前 UI/旋转修复，旧证据可能失效；
2. 现有自动化包含大量源码字符串断言，需要确认真正执行产品逻辑的覆盖范围；
3. HarmonyOS 两产品共用模块权限和大部分代码，需要证明标准版不会携带或触发录屏能力；
4. 当前构建配置没有正式签名，更新、覆盖安装和发布结论尚不能关闭；
5. 截屏、Core Vision OCR、浮窗触摸、内部音频和 MP4 仍需要真机，模拟器不能代替；
6. 大型 `Index.ets`、`BattleOverlayCoordinator.ts` 和 Native 桥接集中承担多个职责，需重点查状态串线、生命周期和资源释放；
7. Release 源码中存在阶段验证页面和辅助入口，需确认最终产物完全不可达且不暴露测试数据；
8. UI 已经历返工，需重新以 Android 当前截图和真实数据检查色彩、溢出、按钮语义、调试种子数据和旋转后的全窗口重排；
9. 更新服务必须筛选 HarmonyOS 正确变体 HAP，不能沿用 Android APK 选择假设；
10. Android 分叉后的共享修复必须逐提交核对，不能因为 HarmonyOS 恰好包含某个修复就认为同步机制可靠。

## 10. 审计阶段验收顺序

最终实际执行按以下顺序推进，前一项发现 P0/P1 时先记录并评估是否阻断后续：

1. 冻结并复现 Android 标准/录屏基线；
2. 生成完整功能—源码—测试—设备映射；
3. 静态审阅 HarmonyOS 权限、变体、构建、Native 和 Release 产物；
4. 运行跨平台数据、伤害、存储、候选和迁移黄金测试；
5. 审计正式主界面、队伍/配置 CRUD、设置和更新；
6. 审计捕获、我方 OCR、双方队伍预览和人工纠正；
7. 审计对局状态、普通浮窗、HUD、单双打和旋转；
8. 审计 replay 录屏、内部音频、媒体库和异常收尾；
9. 完成模拟器全量回归和截图对照；
10. 在 ARM64 真机关闭所有 E5 项；
11. 汇总缺陷，按 P0–P3 修复和复测；
12. 重新构建签名候选，执行覆盖升级、包检查和最终报告签署。

在第 10 步完成前，只能报告“代码/自动化/模拟器范围结果”，不能报告 HarmonyOS 端全部功能正常或可发布。
